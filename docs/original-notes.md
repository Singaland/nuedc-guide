# 电赛经验分享：原始口述整理

> 说明：本文按口述顺序整理，尽量保留原话表达，只做了分段、标点和少量明显错别字修正。

## 1. 团队分工和沟通

首先就是分工。要有一个人做软件、编写代码，一个人做硬件，还要一个人做机械结构设计。

这两个人都要懂代码，硬件只是侧重点不一样。负责软件的同学是主力，必须要对整个项目流程的每个环节非常了解，从系统设计方案、代码编写、引脚分配、传感器选型、车体结构设计，都要全部清楚。

负责做车体结构设计的同学主要是拼车、布局。有时候比赛会对车体长宽高有要求，这个要注意。

整个团队一定要多沟通，确保信息及时共享，不要自己一个人闷头做。

## 2. 我的电赛经历

我参加了 2024 年电赛和 2025 年电赛，都是团队里负责软件的部分。

## 3. 备赛：CCS、MSPM0G3507 和备用板

备赛的话，学习路线大概是这样的。

软件我推荐你们用 CCS，这个是文件夹管理的，并且配引脚特别方便。

单片机的话，我们去年两年都是限制的 MSPM0G3507 芯片，不知道今年还会不会限制了。这款芯片用起来还可以，引脚挺多的，但是前两年官方的这款芯片的保护电路设计得并不好，很容易出现锁机或者烧毁的情况。因此在使用过程中必须特别小心，尽量避免出现这种情况。

一旦锁机，处理起来特别麻烦。所以我建议你们每组手里除了有一块官方申请的板子外，再另外提前准备两块，可以在嘉立创上购买。最好提前买，不然到时候会涨价。

另外就是在比赛期间，一旦芯片烧毁，你再买的话发货也要两天，特别浪费时间。这期间什么都干不了，特别浪费时间，影响进度。

往年其他组和我们组都出现过这种情况，所以你们一定要尽力避免。也就是说在赛前你们手里最好保持着三块芯片的备用量。

## 4. 单片机学习路线

单片机学习路径首先要有单片机的基础知识。

时间充裕的话，先学 B 站江协科技 STM32 单片机教程，可以跟着动手做做，主要是学习和认识单片机，知道原理。

来不及的话，快速过一遍，了解单片机原理。

学完之后可以看 B 站 Torr is-Yin 的《TI MSPM0 快速入门课》，这个讲 3507 的还不错，可以多参考。

硬件控制的话，多看你买的那款硬件的使用说明书。硬件控制类的原理也在江协科技里讲过，这个一定要多注意。

## 5. 视觉、Python 和 C 语言

学习路线补充：视觉这几年考的也挺多。

之前国赛年的送药小车，2023 年国赛年和 2025 年国赛年都考过，感觉以后会越来越重视。所以这个一定要重视。

视觉模块学习的话就是 Python 语言，这个可以看看：

https://www.runoob.com/python3/python3-tutorial.html

如果你的 C 语言掌握得很扎实的话，Python 很快就可以上手了，学一下语法就可以。视觉模块用到的 Python 知识不算特别深。

如果连 C 语言都没看过的话，我推荐去看 MOOC 上的浙大翁恺 C 语言基础和进阶课，跟着写一下课后作业，对你的编程能力和思维提升很大。

## 6. 调试、检查电路和排查故障

下边说一下调试和检查电路、排查故障的问题。

这个问题是比赛过程中最麻烦，也是耗时最多、最影响进程、最需要经验的一部分。

首先就是要掌握一些排查问题的方法和工具。检查代码问题、单片机配置问题，比如说中断没有使能，PWM 占空比不对，分频没有设置好，或者逻辑有问题。

要熟练掌握 CCS 里边的调试功能这个模块。在 Watch 窗口里看看代码里的变量怎么变化，一步步调试看看问题出在哪里，然后修改。

不要一个劲地喂给 AI。不管代码是自己写的，或者 AI 写的，或者借鉴网上相似思路的，在使用之前一定要花时间仔细地阅读一下整个项目工程，弄清楚里边每个函数的作用、功能、逻辑。

这个工作前期看着很浪费时间，但是在后边调试过程中，可以帮你节省大量的时间。

千万不要在没弄懂这个代码逻辑的情况下去盲目修改，这样会有很多无用功。

一定要先读代码！做到胸中有数，脑中有逻辑。

如果写代码的话，一定要管理好工程。不要把所有函数或者功能写到一个文件里边，这样容易后边成为屎山代码，维护起来极度困难。

每个功能单独开个文件。代码里尽量写好注释和你的思路，写清楚，方便后续其他人阅读和自己查看，不然后期也是很浪费时间。

## 7. 电路检查：模块单独测试

电路检查这一块儿也是一个大坑。

如果在检查完软件没有问题的话，接下来就是检查电路。

在检查硬件电路或者某个功能模块的时候，比如灰度循迹、视觉云台瞄准扫描时，不要在一个整个项目里修改一部分，然后去检查某个部件的问题。

测试某个部件就单独写个测试代码，单独拉出来测试，看看功能是否正常。

如果不正常，就检查电路连接问题，看看是不是信号在传输过程中断路了。这个错误经常发生。

这时候就要用万用表来一段线路一段线路地测试，定位问题。

## 8. 万用表测电压和单片机供电

需要注意的一点是，在测试过程中，比如说要测试 TB6612 的 3.3V 或者 5V 供电电压是否正常，一定要把这两个端口接两个杜邦线单独引出来测。

不要拿万用表在原芯片上测，这样极易造成短路，烧毁芯片。这一点需要特别注意！包括单片机也是同样的原理。

还需要注意的一点是单片机供电问题。我总结了一下往年烧毁和锁机芯片的一些经验和案例，大概要注意的几点：

首先不要两端供电。如果你用电脑调试供电，就不要再接电源供电。

如果是外部供电，就一定要检查单片机的使用手册，看看是几伏供电，哪个端口供电。

供电之前先提前测试一下供电电源是否满足要求，再往单片机上接。一定要检查，这些都是血泪史。

另外在前期测试各个功能模块时，尽可能在单片机上只接该模块相关的电路，尽量不要接其他的电路，避免出现问题的时候影响其他部分。

## 9. PWM 波测量

另外就是测 PWM 波的问题。

PWM 波主要是电机控速、控制舵机，所以占空比就很重要。

舵机要求特定频率和占空比的 PWM 波，这个在代码里设置分频的时候要注意一下。

测 PWM 波的话，不要通过计算原电压再乘占空比这种方式测。用学校的示波器测，看波形、频率、占空比是否满足要求。

## 10. 共地问题

还有就是共地问题。

同一套系统的所有设备的 GND 端必须共地。不共地的话有时候会出现参考地不一致，信号电平没有共同参考基准。

比如说单片机的 GND、TB6612 的 GND、灰度传感器的 GND 要共地。

如果有两套系统的话，比如说一套单片机控制小车，另一个是视觉模块，比如 OpenMV、K230 等控制云台，且不与单片机通信的话，这个不需要共地，只要系统内共地就可以了。

## 11. 硬件损坏和备件

另外硬件调试里还有要补充的是，如果检查完软件代码、电路连接都没有问题的话，数据还是不正常，就要考虑硬件损坏的问题。

换一个硬件测试，数据还是不对的话就再换。

实验室里好多器件都损坏了，连着几个硬件用不了很正常。

不过还是建议每一个组有常用的器件以及备用。

在使用前仔细阅读说明书和注意事项。器件买回来后先写个小的测试代码，看看器件功能是否正常，这个也是准备工作之一吧。

## 12. 赛前物资：TB6612

赛前准备的话，有些常用、必不可少且贵的部件，比如说四路驱动的 TB6612，这个比较贵，我记得当时是 50 多一个，并且还很容易烧毁损坏。

我的建议是在嘉立创上多打印几块这种原板子，然后自己买电阻、电容、其他部件自己焊接。这样的话成本低一些。

每个组赛前这种四驱的 TB6612 驱动模块至少准备两块吧。

另外焊完板子不要立马使用，先用万用表蜂鸣器功能，每个部分测试一下看看有没有问题，没问题了再使用。

## 13. 灰度传感器

还有几个就是灰度传感器，这是个老大难的问题。

我们队两年都死在这一问上。市面上很多灰度传感器真的是又贵又难用。

有些路数太多的话，不太好设置各种状态，遇到直角转弯就很难受，极度不稳定。

路数少有时候又会因为扫描区域太小，有盲区等其他的问题。

还有些灰度传感器就是自动调节阈值的，这个也是个坑。要么就是太灵敏，总是误报；要么就是太不灵敏，一直检测不到。

所以我的建议是多买几款，多收集一下信息，看哪些比较好用，自己试试。

## 14. 常用功能模块提前写好

另外就是各个常用的功能模块在比赛前尽可能提前写完，测试好，确保能用。

比如说灰度循迹模块、二维云台追踪定位、视觉检测或者循迹几个常用的可以提前写好，到时候可以节省很多时间。

## 16. AI 编程和 Vibe Coding

还有一部分就是 AI 编程的了，也就是常说的 “vibe coding”。

国外的像 Codex、Claude，国内的像 DeepSeek V4 等模型，编程很厉害。最近几个月我也在用，怎么说呢，编程确实很厉害，也确实可以完成一些项目。

同一款模型在不同的人手里发挥的作用完全不一样的。要想用得厉害，也是有些 trick 在里边的。

对我们电气电子专业的人来说可能有些陌生，我就大概说一下使用 AI 的一些方法和思路。

首先就是一定要有“提示词”的概念，也就是 Prompt。

什么意思呢？就是有时候一些事情不是 AI 做不了，而是你没有给它说清楚，也就是提示词不对，导致输出的结果很差。

所以我们的工作就是想一个好的提示词，让 AI 输出我们想要的东西。

现在的 AI 都是根据上下文回答的，所以你在提示词里边一定要交代清楚你的项目背景、整个系统框架、技术细节、你用的什么软件版本、型号、配置、硬件以及硬件说明书。

最好是给它一些 few-shot，也就是少量示例。如果没有的话可以不给。

只有这些都交代清楚了，AI 才会给你一个好的答案。

## 17. 上下文管理

这就要求我们做好上下文管理和避免上下文污染。

因为如果上下文有问题的话，AI 就会输出你不要的答案。

做上下文管理的话，我建议就是每个项目都做一个 Markdown 文件，也就是 `.md` 文件。

每次跟 AI 对话前，先让它读一下项目的 md 文件，有了上下文信息再跟你对话。

对话完之后，就让 AI 及时更新 md 文件，以避免重启模型后上下文丢失。

至于用哪款 AI，有条件的话还是用 GPT、Codex、Claude 这种。这些模型幻觉还是比较低的，相较于其他模型，编程能力也强。

没条件的话就用 Claude 的架构，后端接 DeepSeek V4。

## 18. Codex、Claude Code 这种 Agent 怎么用

接下来我讲一下 Codex、Claude 这种 Agent 怎么用。

Codex、Claude Code 这种 Agent 可以直接安装在 Windows 的 PowerShell 里使用。

最稳的方式是先去官方文档找 Windows 安装命令，或者让 GPT / DeepSeek 帮你查最新官方命令。

如果使用 npm 安装方式，需要先安装 Node.js。

如果使用官方 Windows 原生安装脚本，则不一定需要手动安装 Node.js。

国内网络环境下，可能还需要给 PowerShell、npm 或系统环境变量配置代理。

如果使用官方 Claude / OpenAI，就用它们自己的账号登录或 API Key。

如果 Claude Code 想接 DeepSeek，可以配置 DeepSeek 的 Anthropic-compatible API。

但 Codex 想接第三方后端时，通常需要额外配置 provider，不只是换 API Key。

安装或运行时报错，可以把完整报错复制给 AI 分析，但必须先把 API Key、Token、密码、私有仓库地址等敏感信息打码。

## 19. Agent 做项目的工作流

使用这些 Agent 做项目的时候，如果你的软件可以打开终端或者 PowerShell，直接在软件的终端里运行 Codex 或者 Claude 就可以。

CCS 一般可以。如果不可以，就把你的项目路径给 Agent，让它进入你的项目空间里阅读修改。

用的时候不要直接说“给我生成什么什么”。

先按 `Shift + ~` 切换为 Plan Mode 模式，在命令行下方。你去跟它交流，让它提问你问题，确定整个项目框架和所有技术细节，确定 AI 不会乱写的时候，把这个规划单独导出。

然后再喂给 AI，让它统一编程。

不要一段一段给它说，让它写。这样太低效了，还容易写出屎山，后期很难管理维护。
