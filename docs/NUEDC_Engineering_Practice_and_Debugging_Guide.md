# 电赛经验分享：备赛与避坑记录

## 0. 写在前面

这篇内容主要整理一些电赛备赛和比赛过程中的实际经验，包括团队分工、备赛学习路线、软件调试、硬件排故、常用模块准备，以及最近比较常用的 AI 编程工具怎么用。

这些内容不是官方教程，更多是偏实战的经验记录。里面有些观点可能不一定适用于所有队伍和所有题目，但可以作为备赛、调试和排坑时的参考。

## 1. 近几年题目趋势：小车和视觉要重视

从这几年的电赛题目来看，小车类题目还是比较多的，而且视觉相关内容也越来越常见。

之前国赛年的送药小车，还有 2023 年、2025 年国赛年都考过视觉相关的内容。我个人感觉以后视觉会越来越受重视，所以这部分一定不能完全忽略。

备赛的时候，建议重点关注这些方向：

- 小车底盘和运动控制
- 电机驱动和编码器测速
- 灰度循迹
- 视觉识别
- 视觉循迹
- 云台追踪和定位
- 单片机和视觉模块之间的通信

不要等到比赛题目出来之后才从零开始学视觉或者小车控制，那样时间会非常紧。

## 2. 团队分工：一定要有人懂全局

电赛团队里，分工一定要明确。

一般来说，至少要有：

- 一个人负责软件，主要写代码、调试程序、控制整个系统逻辑
- 一个人负责硬件，主要处理电路、模块连接、传感器、电机驱动这些
- 一个人负责机械结构设计，主要拼车、布局、安装传感器和执行机构

但是这里要注意，软件和硬件这两个人都要懂代码，只是侧重点不一样。

负责软件的同学一般是主力，必须对整个项目流程的每个环节都比较清楚，不能只会写代码。比如：

- 系统设计方案
- 代码编写
- 引脚分配
- 传感器选型
- 硬件模块之间怎么连
- 车体结构设计
- 各个模块怎么配合

因为最后所有东西都要在代码里统一控制，所以软件负责人必须理解整个系统。

负责车体结构设计的同学，主要是拼车和布局。有时候比赛会对车体的长、宽、高有要求，这个一定要提前注意，不然后面车拼好了发现尺寸不符合要求，就很麻烦。

整个团队一定要多沟通，确保信息及时共享。不要自己一个人闷头做。很多时候问题不是技术本身多难，而是信息没有同步，比如软件不知道硬件引脚改了，结构不知道传感器要装在哪里，硬件不知道空间已经不够了，最后就会返工。

## 3. 备赛学习路线

### 3.1 先学单片机基础

单片机学习路线大概是这样的。

如果时间充裕，建议先去看 B 站江协科技的 STM32 单片机教程。这里不是说你比赛一定用 STM32，而是通过这个教程先认识单片机，知道单片机的基本原理。

主要要了解：

- GPIO 是什么
- PWM 是什么
- ADC 是什么
- 串口怎么通信
- 定时器怎么用
- 单片机怎么控制硬件
- 程序、引脚、外设之间是什么关系

如果时间够，最好跟着动手做一做。这样后面换到比赛指定芯片的时候，上手会快很多。

如果时间来不及，也建议快速过一遍，至少要知道单片机大概是怎么工作的。

### 3.2 CCS 和 MSPM0G3507

软件开发环境方面，我推荐用 CCS。

CCS 是文件夹管理的，工程结构比较清楚，而且配置引脚比较方便，很适合电赛这种需要频繁调试、改引脚、管理多个模块代码的项目。

单片机的话，我们 2024 年和 2025 年用的都是官方限制的 MSPM0G3507，不知道今年还会不会继续限制这款芯片，具体还是要以当年官方通知为准。

这款芯片用起来还可以，引脚挺多的，但是前两年官方这款芯片的保护电路设计得并不好，很容易出现锁机或者烧毁的情况。所以使用过程中必须特别小心。

一旦锁机，处理起来特别麻烦。如果比赛期间芯片烧毁了，你再买的话，发货也要两天左右，这段时间基本什么都干不了，非常浪费时间，也非常影响进度。

所以我的建议是，每组手里除了官方申请的一块板子之外，最好再另外提前准备两块，可以在嘉立创上购买。最好提前买，不然后面可能会涨价。

往年其他组和我们组都出现过烧板、锁机这种情况，所以一定要尽力避免。赛前每组手里最好保持三块左右开发板备用量。

### 3.3 MSPM0G3507 学习资料

学完单片机基础之后，可以去看 B 站 Torr is-Yin 的《TI MSPM0 快速入门课》，这个讲 MSPM0G3507 还不错，可以多参考。

学习的时候不要只看代码怎么写，还要理解为什么这么配置，比如引脚、外设、定时器、PWM、串口这些东西是怎么对应起来的。

### 3.4 硬件控制要多看说明书

硬件控制的话，一定要多看你买的那款硬件的使用说明书。

比如传感器、电机驱动、舵机、编码器、视觉模块，都要看清楚：

- 供电电压
- 引脚定义
- 通信方式
- 控制协议
- 示例代码
- 注意事项

很多硬件控制类的原理，江协科技里面也讲过，这个一定要多注意。

## 4. 视觉、Python 和 C 语言基础

视觉这几年考得挺多，我感觉以后会越来越重要，所以这个一定要重视。

视觉模块主要用 Python。Python 可以看菜鸟教程：

https://www.runoob.com/python3/python3-tutorial.html

如果你的 C 语言掌握得比较扎实，Python 很快就能上手，学一下基本语法就可以。视觉模块用到的 Python 知识不算特别深，重点是能看懂代码、能改参数、能跑通流程。

如果连 C 语言都没系统学过，我推荐先去看 MOOC 上浙江大学翁恺老师的 C 语言基础和进阶课，跟着写一下课后作业。这个对编程能力和编程思维提升很大。

不要觉得 C 语言只是为了考试。电赛里写单片机代码、读别人代码、调试程序，最后都离不开基本的编程能力。

## 5. 软件调试和代码管理

调试和排查故障，是比赛过程中最麻烦、最耗时、最影响进程，也最需要经验的一部分。

首先要掌握一些排查问题的方法和工具。检查代码问题、单片机配置问题的时候，要重点看：

- 中断有没有使能
- PWM 占空比对不对
- 定时器分频有没有设置好
- 引脚配置和实际接线是不是一致
- 程序逻辑有没有问题
- 变量变化是不是符合预期

一定要熟练掌握 CCS 里的调试功能，尤其是 Watch 窗口。可以在 Watch 窗口里看代码里的变量怎么变化，配合断点和单步调试，一步步看问题出在哪里，然后再修改。

不要一个劲地把问题喂给 AI。代码不管是自己写的，还是 AI 写的，还是借鉴网上相似思路的，在使用之前都一定要花时间仔细阅读整个项目工程。

你要弄清楚：

- 每个文件是干什么的
- 每个函数的作用是什么
- 主程序流程是什么
- 各个模块之间怎么调用
- 哪些变量在哪里被修改
- 外设初始化和控制逻辑是不是匹配

这个工作前期看着很浪费时间，但是后面调试的时候可以帮你节省大量时间。

千万不要在没弄懂代码逻辑的情况下盲目修改，这样会做很多无用功，甚至把原来能跑的部分也改坏。

一定要先读代码，做到胸中有数，脑中有逻辑。

如果自己写代码，也一定要管理好工程。不要把所有函数或者功能都写到一个文件里，这样后面很容易变成很难维护的代码。

建议每个功能单独开文件，比如：

- 电机控制
- 舵机控制
- 传感器读取
- 编码器处理
- PID 控制
- 串口通信
- 视觉数据接收
- 主流程逻辑

代码里尽量写好注释，把你的思路写清楚，方便后续其他人阅读，也方便自己回头查看。不然后期会非常浪费时间。

## 6. 硬件电路检查和排查故障

电路检查也是一个大坑。

如果检查完软件没有问题，接下来就要检查电路。

在检查硬件电路或者某个功能模块的时候，比如灰度循迹、视觉云台、瞄准扫描，不要在整个大项目里改一部分，然后去检查某个部件的问题。

测试某个部件，就单独写一个测试代码，把它单独拉出来测试，看看功能是否正常。

如果不正常，再检查电路连接问题，看看是不是信号在传输过程中断路了。这个错误经常发生。

这时候就要用万用表，一段线路一段线路地测试，定位问题在哪里。

比如：

- 单片机引脚到杜邦线是否导通
- 杜邦线到模块接口是否导通
- 模块供电是否正常
- GND 是否连接正确
- 信号线有没有断路

不要只看表面接没接上，很多线看起来接上了，其实内部可能已经断了。

## 7. 用万用表测电压时一定要小心

这里有一点特别重要。

比如要测试 TB6612 的 3.3V 或者 5V 供电电压是否正常，一定要把这两个端口接两根杜邦线单独引出来测。

不要直接拿万用表在原芯片或者密集引脚上测，这样非常容易造成短路，烧毁芯片。

单片机也是同样的原理。

凡是引脚比较密、容易短路的位置，都尽量引出来测，不要直接拿表笔在板子上硬测。

## 8. 单片机供电问题

单片机供电一定要特别注意。

我总结了一下往年烧毁和锁机芯片的一些经验和案例，大概要注意这几点：

第一，不要两端供电。

如果你用电脑 USB 调试供电，就不要再接外部电源供电。

如果是外部供电，一定要先检查单片机使用手册，看清楚：

- 需要几伏供电
- 从哪个端口供电
- 供电电压范围是多少
- 有没有特殊注意事项

供电之前，先用万用表测试一下供电电源是否满足要求，再往单片机上接。

这些都是血泪史，一定要检查。

前期测试各个功能模块时，也尽可能在单片机上只接当前模块相关的电路，尽量不要接其他电路。这样如果出现问题，也不会影响其他部分，排查起来也更简单。

## 9. PWM 波要用示波器测

PWM 波主要用于电机控速和舵机控制，所以占空比很重要。

尤其是舵机，一般要求特定频率和特定占空比的 PWM 波。这个在代码里设置定时器分频、周期和占空比的时候要特别注意。

测 PWM 波的时候，不要通过“原电压乘占空比”这种方式去估算。

要用学校的示波器测，看实际波形、频率、占空比是否满足要求。

示波器看到的才是真实输出信号，不能只靠计算。

## 10. 共地问题

共地问题也非常重要。

同一套系统里的所有设备，GND 必须共地。专业一点说，就是它们需要有共同的参考地，否则信号电平没有共同参考基准，可能会导致信号识别异常。

比如一套单片机控制小车系统里：

- 单片机 GND
- TB6612 的 GND
- 灰度传感器的 GND
- 其他和单片机有信号连接的模块 GND

这些都要共地。

如果不共地，即使信号线接对了，也可能因为参考地不一致，导致高低电平识别不正常。

但是如果有两套完全独立的系统，比如一套单片机控制小车，另一套视觉模块，比如 OpenMV、K230 控制云台，并且这两套系统之间不通信、没有信号连接，那就不一定需要共地。

判断原则就是：

有信号连接或通信关系的模块，必须有共同参考地；完全独立、没有信号连接的系统，只需要各自系统内部共地。

## 11. 软件和电路都没问题时，要考虑硬件损坏

如果检查完软件代码、电路连接、供电、共地之后，数据还是不正常，就要考虑硬件损坏的问题。

这时候不要一直在代码里改来改去，可以换一个硬件测试。

如果数据还是不对，就再换一个。

实验室里很多器件其实都已经损坏了，连续几个硬件用不了也很正常。所以不要默认你手里的器件一定是好的。

建议每个组都准备常用器件和备用件。

器件买回来之后，不要直接装到最终项目里。先仔细阅读说明书和注意事项，然后写一个小测试代码，看看器件功能是否正常。

这也是备赛准备工作的一部分。

## 12. TB6612 和驱动模块准备

赛前准备里，有些常用、必不可少而且比较贵的部件，一定要提前准备。

比如四路驱动的 TB6612，这个比较贵。我记得当时是 50 多一个，而且还很容易烧毁损坏。

我的建议是，可以在嘉立创上多打几块这种原理图和 PCB 比较成熟的板子，然后自己买电阻、电容和其他元件回来焊接。这样成本会低一些，也方便多准备几块。

每个组赛前这种四驱 TB6612 驱动模块至少准备两块。

另外，焊完板子不要立马使用。先用万用表蜂鸣器功能，也就是通断档，把每个关键部分测试一下，看看有没有短路、虚焊、连锡。确认没问题了再上电使用。

## 13. 灰度传感器是老大难问题

灰度传感器真的是一个老大难问题。

我们队两年都死在这一块上。

市面上很多灰度传感器真的又贵又难用。有些路数太多，不太好设置各种状态，遇到直角转弯就很难受，稳定性很差。

路数少的话，有时候又因为扫描区域太小，存在盲区。

还有些灰度传感器是自动调节阈值的，这个也是一个坑。要么太灵敏，总是误报；要么太不灵敏，一直检测不到。

所以我的建议是，多买几款，多收集一下信息，看哪些比较好用，然后自己实际测试。

不要只看商家的宣传。一定要在自己的车、自己的赛道、自己的光照条件下试。

## 14. 常用功能模块要提前写好

各个常用功能模块，比赛前尽可能提前写完、测试好，确保能用。

比如：

- 灰度循迹模块
- 二维云台追踪定位
- 视觉检测
- 视觉循迹
- 电机控制
- 舵机控制
- 编码器测速
- PID 控制
- 串口通信

这些模块不一定比赛时能原封不动使用，但提前写好、测试好，到时候可以节省很多时间。

比赛期间最宝贵的就是时间，不要等题目出来之后所有东西都从零开始写。更好的状态是题目出来之后，根据要求去组合、修改、调参。

## 15. AI 编程和 Vibe Coding

还有一部分就是 AI 编程，也就是常说的 vibe coding。

国外的像 GPT、Codex、Claude，国内的像 DeepSeek 等模型，编程能力都很厉害。最近几个月我也在用，怎么说呢，编程确实很厉害，也确实可以完成一些项目。

但是同一款模型，在不同的人手里发挥的作用完全不一样。

要想用得厉害，也是有一些技巧在里面的。对我们电气电子专业的人来说，这些东西可能有点陌生，所以我大概说一下使用 AI 的一些方法和思路。

## 16. 一定要有 Prompt 的概念

首先就是一定要有“提示词”的概念，也就是 Prompt。

什么意思呢？

有时候一些事情不是 AI 做不了，而是你没有给它说清楚。也就是提示词不对，导致输出结果很差。

所以我们要做的事情，就是想一个好的提示词，让 AI 输出我们想要的东西。

现在的 AI 都是根据上下文回答的，所以你在提示词里一定要交代清楚：

- 项目背景
- 整个系统框架
- 技术细节
- 用的什么软件版本
- 芯片型号
- 单片机配置
- 引脚分配
- 使用了哪些硬件
- 硬件说明书里的关键参数
- 当前出现了什么问题
- 已经排查了哪些问题
- 你希望它输出什么

最好还能给它一些 few-shot，也就是少量示例。如果没有示例也可以不给，但项目背景和技术细节一定要尽量交代清楚。

只有这些都说清楚了，AI 才更可能给你一个好的答案。

## 17. 上下文管理和上下文污染

使用 AI 的时候，还要做好上下文管理，避免上下文污染。

因为 AI 是根据上下文回答的。如果上下文里有错误信息、过期方案、已经废弃的代码逻辑，AI 就可能沿着错误方向继续输出。

我的建议是，每个项目都做一个 Markdown 文件，也就是 `.md` 文件。

这个文件里记录：

- 项目目标
- 系统框架
- 硬件清单
- 引脚分配
- 软件结构
- 每个模块的功能
- 当前已经完成了什么
- 还有什么问题
- 调试记录
- 注意事项

每次跟 AI 对话前，先让它读一下项目的 Markdown 文件，有了上下文信息之后再和你对话。

对话完之后，再让 AI 及时更新这个 Markdown 文件，避免重启模型或者换对话之后上下文丢失。

这个习惯非常重要。

## 18. 用哪款 AI

至于用哪款 AI，有条件的话还是用 GPT、Codex、Claude 这种。这些模型相对来说幻觉低一些，编程能力也比较强。

没条件的话，也可以用 Claude Code 这种架构，后端接 DeepSeek 等模型。

但是无论用哪款，都不要把 AI 当成完全替代你的人。AI 只是工具，最终代码能不能用，还是要你自己读懂、测试、调试。

## 19. Codex、Claude Code 这种 Agent 怎么用

Codex、Claude Code 这种 Agent 和普通聊天 AI 不太一样。

它们可以直接在本地项目里读取文件、理解工程结构、执行命令、修改代码，更适合做真实项目。

这些 Agent 可以直接安装在 Windows 的 PowerShell 里使用。

最稳的方式是先去官方文档找 Windows 安装命令，或者让 GPT / DeepSeek 帮你查最新官方命令。因为这些工具更新很快，不建议一直用很老的教程。

如果使用 npm 安装方式，需要先安装 Node.js。

如果使用官方 Windows 原生安装脚本，则不一定需要手动安装 Node.js。

国内网络环境下，可能还需要给 PowerShell、npm 或系统环境变量配置代理。

如果使用官方 Claude / OpenAI，就用它们自己的账号登录或 API Key。

如果 Claude Code 想接 DeepSeek，可以配置 DeepSeek 的 Anthropic-compatible API。

但 Codex 想接第三方后端时，通常需要额外配置 provider，不只是换 API Key。这个要按照具体工具的配置方式来。

## 20. 报错可以给 AI，但敏感信息必须打码

安装或运行时报错，可以把完整报错复制给 AI 分析。

但是一定要先把敏感信息打码，比如：

- API Key
- Token
- 密码
- Cookie
- 私有仓库地址
- 个人不想暴露的路径
- 服务器地址
- 其他认证信息

不要把密钥原样发给 AI，也不要发到公开网站上。

## 21. Agent 做项目的工作流：先 Plan，再 Code

使用这些 Agent 做项目的时候，如果你的软件可以打开终端或者 PowerShell，就直接在软件的终端里运行 Codex 或者 Claude。

CCS 一般可以打开终端。如果不可以，就把你的项目路径给 Agent，让它进入你的项目空间里阅读和修改。

用的时候不要直接说“给我生成什么什么代码”。

更好的做法是先进入 Plan Mode 模式。比如有些工具可以按 `Shift + ~` 切换到 Plan Mode，位置一般在命令行下方。

进入 Plan Mode 之后，先跟它交流，让它提问你问题，确认整个项目框架和所有技术细节。

比如让它问清楚：

- 项目目标是什么
- 用什么芯片
- 用哪些硬件模块
- 引脚怎么分配
- 每个模块负责什么功能
- 模块之间怎么通信
- 哪些代码已经有了
- 哪些代码需要新增
- 哪些文件不能乱改
- 有哪些比赛规则限制

等这些都确定清楚，AI 不会乱写的时候，再让它把规划单独导出成 Markdown 文档。

然后再把这份规划喂给 AI，让它统一编程。

不要一段一段地跟它说，然后让它一段一段写。这样太低效了，而且很容易写出很难维护的代码，后期管理起来非常困难。

更推荐的流程是：

1. 项目先有一个 Markdown 说明文档
2. 让 Agent 读取项目上下文
3. 进入 Plan Mode
4. 让 Agent 提问补齐细节
5. 输出完整规划
6. 保存规划文档
7. 再按规划统一实现
8. 最后自己检查、测试、调试

核心就是一句话：

不是先让 AI 写代码，而是先让 AI 和你一起把项目想清楚。

## 22. 最后总结

电赛真正难的地方，不只是会不会写代码，也不只是会不会接电路。

它更考验的是一个团队把软件、硬件、结构、调试、排故、时间管理这些东西整合起来的能力。

我的建议简单总结一下：

- 团队分工要明确，但核心成员要懂全局
- 软件负责人不能只会写代码，要理解整个系统
- 赛前一定要准备备用板、备用模块和常用器件
- 单片机、C 语言、Python、视觉都要提前学一点
- 常用模块要提前写好并测试
- 调试时先读代码，不要盲改
- 硬件排查要用万用表、示波器，一步步定位
- 同一系统有信号连接的模块必须共地
- 不要默认硬件一定是好的，坏模块很常见
- AI 编程很好用，但前提是 Prompt 清楚、上下文清楚、自己能读懂代码
- Agent 做项目要先规划，再统一实现

希望这些经验能给后续备赛的人提供一些参考，少踩一些重复的坑。
