# 全国大学生电子设计竞赛备赛指南

这是一份面向电赛新手的备赛与避坑指南，内容整理自小车类、控制类项目中的软件调试、硬件排查、模块准备和 AI 编程辅助经验。

本文不是官方教程，也不替代当年竞赛通知、题目要求和器件手册。芯片型号、开发环境、比赛规则、器件选型都应以当年官方文件和实际项目需求为准。

## 适合谁阅读

- 准备参加全国大学生电子设计竞赛的低年级同学
- 刚开始接触单片机、小车、视觉模块的同学
- 负责软件、硬件或结构，但还不清楚团队协作方式的同学
- 想系统了解调试排故、备件准备和 AI 辅助编程方法的同学

## 总体建议

近几年电赛中，小车类题目出现频率较高，视觉相关任务也越来越常见。备赛时不要只准备最基础的单片机控制，还应提前接触小车运动控制、灰度循迹、视觉识别、云台控制和模块通信。

电赛真正考验的不只是某个单点技术，而是团队把软件、硬件、结构、调试、排故和时间管理整合起来的能力。赛前能提前准备的内容越多，比赛期间就越不容易被基础问题卡住。

## 团队分工与协作

一个常见的小车类队伍可以按以下方向分工：

| 方向 | 主要职责 | 注意事项 |
| --- | --- | --- |
| 软件 | 代码编写、系统逻辑、调试流程、模块联调 | 软件负责人需要理解整个系统，而不只是写代码 |
| 硬件 | 电路连接、模块选型、供电检查、信号排查 | 硬件同学也应具备基本代码和调试能力 |
| 机械结构 | 车体搭建、空间布局、传感器和执行机构安装 | 注意题目对长宽高、安装位置和稳定性的限制 |

软件和硬件不是完全割裂的分工。负责软件的同学通常需要了解系统设计方案、代码结构、引脚分配、传感器选型、硬件连接和车体结构。最终所有模块都要通过程序统一控制，所以软件负责人必须对项目全局有清晰认识。

团队成员要及时共享信息，不要各自闷头做。很多返工不是因为技术本身很难，而是因为软件不知道硬件引脚改了，硬件不知道结构空间不够，结构设计没有考虑传感器安装位置。

## 备赛学习路线

### C 语言基础

如果 C 语言基础薄弱，建议先补 C 语言，再进入单片机和视觉模块学习。可以参考浙江大学翁恺老师的 C 语言基础和进阶课程，并跟着完成课后作业。

重点不是背语法，而是建立基本编程思维：

- 变量、循环、函数、数组和指针
- 程序如何拆分成模块
- 如何把实际问题转成代码逻辑
- 如何阅读和调试别人写的代码

### 单片机基础

时间充裕时，可以先学习江协科技 STM32 单片机教程。学习 STM32 的目的不一定是比赛直接使用 STM32，而是建立单片机基础认知。

需要重点理解：

- GPIO
- PWM
- ADC
- 串口通信
- 定时器
- 中断
- 单片机如何控制外部硬件
- 程序、引脚和外设之间的关系

时间紧张时，也应快速过一遍基础概念，至少知道单片机程序和硬件外设是如何配合工作的。

### CCS 与 MSPM0G3507

开发环境方面，CCS 比较适合电赛中频繁修改引脚、管理多个模块和进行调试的场景。建议赛前熟悉工程创建、文件管理、引脚配置和 Debug 功能。

前两年有比赛限制使用 MSPM0G3507。该芯片引脚较多，整体可用，但使用时要特别注意供电和接线风险。往年出现过锁机或烧毁的情况，一旦比赛期间开发板损坏，会严重影响进度。

建议每组赛前保持约三块开发板备用量：

| 类型 | 建议数量 | 原因 |
| --- | --- | --- |
| 官方申请板 | 1 块 | 作为基础开发板 |
| 备用板 | 2 块 | 应对锁机、烧毁、临时损坏 |

芯片型号是否继续限制，应以当年官方通知为准。

### 视觉与 Python

视觉相关内容近几年越来越常见。备赛时应至少能跑通基础视觉流程，并理解视觉模块与主控之间的通信方式。

视觉模块通常会用到 Python。如果 C 语言基础扎实，Python 上手会比较快。视觉项目中用到的 Python 知识一般不会特别深，重点是能看懂、能修改、能运行代码。

可参考：

- 菜鸟教程 Python3 教程：<https://www.runoob.com/python3/python3-tutorial.html>
- OpenMV、K230 等视觉模块的官方文档和示例

### 硬件控制

控制任何硬件模块前，都应阅读对应说明书，至少确认：

- 供电电压
- 引脚定义
- 通信方式
- 控制协议
- 示例代码
- 注意事项

很多问题不是代码语法错误，而是没有理解硬件模块的控制方式，或者没有按说明书正确接线和供电。

## 赛前硬件与模块准备

### 推荐备件清单

| 器件或模块 | 建议准备 | 主要原因 |
| --- | --- | --- |
| MSPM0G3507 开发板 | 约 3 块 | 防止锁机、烧毁后项目停摆 |
| TB6612 四路驱动模块 | 至少 2 块 | 常用、较贵、调试中容易损坏 |
| 灰度传感器 | 多买几款测试 | 不同模块稳定性差异很大 |
| 舵机、电机、编码器 | 按项目准备备用 | 执行机构损坏会直接影响测试 |
| 杜邦线、排针、连接线 | 多准备 | 断线、虚接、接触不良很常见 |
| 常用通信模块 | 视项目准备 | 串口、视觉模块通信常用 |

### TB6612 驱动模块

四路 TB6612 驱动模块常用但价格较高，调试中也容易损坏。可以考虑提前在嘉立创等平台打几块成熟原理图和 PCB 的板子，再购买电阻、电容和其他元件自行焊接，降低备件成本。

自己焊接的板子不要立刻上电使用。应先用万用表蜂鸣器档检查：

- 电源和 GND 是否短路
- 相邻引脚是否连锡
- 关键引脚是否虚焊
- 输入输出端是否与原理图一致

确认没有明显问题后再接入单片机和整车系统。

### 灰度传感器

灰度传感器是小车类题目中非常容易踩坑的模块。常见问题包括：

- 路数多时状态设置复杂
- 路数少时扫描区域小，可能存在盲区
- 自动阈值模块可能误报或漏检
- 遇到直角转弯时不稳定
- 商家标称效果和实际赛道表现差异较大

建议多买几款不同类型的灰度传感器，提前在自己的车体、赛道和光照条件下实测，不要只看商品介绍。

### 常用功能模块

以下模块建议赛前提前写好并单独测试：

- 灰度循迹
- 二维云台追踪定位
- 视觉检测
- 视觉循迹
- 电机控制
- 舵机控制
- 编码器测速
- PID 控制
- 串口通信

比赛期间不一定能原封不动使用这些模块，但提前准备可以把比赛中的工作量从“从零开始写”降低为“组合、修改和调参”。

## 软件调试与代码管理

调试和排查故障通常是比赛过程中最耗时、最影响进度的部分。排查时不要只靠猜，也不要一出问题就把代码丢给 AI。

### 代码与配置检查

先检查以下问题：

- 中断是否使能
- PWM 占空比是否正确
- 定时器分频是否合理
- 引脚配置是否和实际接线一致
- 程序逻辑是否符合预期
- 变量变化是否符合预期

CCS 的断点、单步调试和 Watch 窗口非常重要。通过 Watch 窗口观察变量变化，可以逐步判断程序是否进入了预期流程。

### 阅读代码

无论代码来自自己、队友、AI 还是网上案例，使用前都要读懂工程结构。

需要弄清楚：

- 每个文件负责什么功能
- 每个函数的作用是什么
- 主程序流程是什么
- 模块之间如何调用
- 关键变量在哪里被修改
- 外设初始化和控制逻辑是否匹配

不要在没理解逻辑的情况下盲目修改代码。前期读代码看似慢，后期调试时会节省大量时间。

### 工程结构

不要把所有功能都写进一个文件。建议按功能拆分：

- 电机控制
- 舵机控制
- 传感器读取
- 编码器处理
- PID 控制
- 串口通信
- 视觉数据接收
- 主流程逻辑

关键逻辑、参数含义和调试经验应写清楚注释，方便队友阅读，也方便后期维护。

## 硬件排查与安全检查

### 模块单独测试

测试某个模块时，不要直接在完整项目中修改一小段代码来判断问题。更稳妥的方法是为该模块单独写最小测试程序。

适合单独测试的模块包括：

- 灰度循迹模块
- 电机驱动模块
- 舵机模块
- 视觉云台
- 编码器
- 通信模块

这样可以减少其他模块干扰，更快判断问题来自代码、接线、供电还是硬件本身。

### 万用表检查线路

如果模块功能不正常，应使用万用表逐段排查：

- 单片机引脚到连接线是否导通
- 连接线到模块接口是否导通
- 模块供电是否正常
- GND 是否连接正确
- 信号线是否断路

不要只凭肉眼判断杜邦线是否接好。线看起来插上了，不代表内部一定导通。

### 测电压时避免短路

测试 TB6612、单片机或其他密集引脚模块的 3.3V/5V 电压时，不建议直接拿表笔在芯片或密集焊点上测。

更安全的做法是把待测端口用杜邦线引出来，再在杜邦线末端测量。这样可以降低表笔滑动导致短路、烧毁芯片的风险。

### 单片机供电

单片机供电前必须确认：

- 不要 USB 和外部电源两端同时供电
- 外部供电前先查使用手册
- 确认供电电压和供电端口
- 接入单片机前先用万用表测电源是否满足要求

前期测试功能模块时，尽量只接当前模块相关电路，减少故障影响范围。

### PWM 测量

PWM 常用于电机调速和舵机控制。频率和占空比都很重要，尤其是舵机通常要求特定频率和占空比范围。

不要只用“电压乘占空比”的方式估算 PWM。应使用示波器观察实际波形、频率和占空比。

### 共地

同一套系统内，有信号连接或通信关系的模块必须共地。否则会因为参考地不一致，导致信号电平没有共同参考基准，进而出现识别异常。

例如小车控制系统中通常需要共地：

- 单片机 GND
- TB6612 GND
- 灰度传感器 GND
- 其他与单片机有信号连接的模块 GND

如果是完全独立的两套系统，例如单片机控制小车，OpenMV 或 K230 独立控制云台，且两者没有通信和信号连接，则只需要各自系统内部共地。

### 硬件损坏

当软件、配置、供电、接线和共地都检查后，数据仍然异常，应考虑硬件本身损坏。

实验室中的器件可能已经损坏，连续几个模块不可用也并非不可能。此时应换同型号硬件交叉测试，而不是一直在代码里盲改。

新器件买回来后，也应先阅读说明书，再写小测试程序验证功能。

## 常见排障 Checklist

### 软件侧

- [ ] 中断是否使能
- [ ] PWM 占空比是否正确
- [ ] 定时器分频是否设置正确
- [ ] 引脚配置是否和实际接线一致
- [ ] 程序是否进入预期函数
- [ ] Watch 窗口中的变量变化是否符合预期
- [ ] 代码逻辑是否已读懂后再修改

### 硬件侧

- [ ] 模块是否单独写测试程序验证
- [ ] 供电电压是否正确
- [ ] GND 是否连接正确
- [ ] 有信号连接的模块是否共地
- [ ] 信号线是否逐段测通过
- [ ] 是否避免在密集芯片引脚上直接测电压
- [ ] PWM 是否用示波器测过实际频率和占空比
- [ ] 是否换模块排除硬件损坏

### 赛前准备

- [ ] 开发板是否有备用
- [ ] TB6612 或其他驱动模块是否有备用
- [ ] 灰度传感器是否实测过多款
- [ ] 常用功能模块是否提前写好并测试
- [ ] 新买器件是否先单独测试
- [ ] 关键模块说明书是否保存并读过

## AI 编程辅助

AI 编程可以提高效率，但效果取决于使用方式。常见工具包括 GPT、Codex、Claude、DeepSeek 等。AI 不能替代对项目的理解，生成代码后仍然需要人工阅读、测试和调试。

### Prompt 信息清单

向 AI 提问时，应尽量提供完整上下文：

- 项目背景
- 系统框架
- 使用的软件版本
- 芯片型号
- 单片机配置
- 引脚分配
- 硬件模块型号
- 说明书关键参数
- 当前代码逻辑
- 当前异常现象
- 已经排查过哪些问题
- 期望输出什么形式的结果

如果有示例，可以提供 few-shot，例如已有代码风格、模块接口形式、期望输出格式。

### 上下文管理

建议每个项目维护一个 Markdown 文档，记录：

- 项目目标
- 系统结构
- 硬件清单
- 引脚分配
- 模块功能
- 代码结构
- 当前问题
- 调试记录
- 注意事项

每次和 AI 对话前先让它读取该文档，对话结束后再更新文档，避免重启模型后上下文丢失，也避免上下文污染。

### Codex / Claude Code Agent 工作流

Codex、Claude Code 这类 Agent 可以读取本地项目、理解工程结构、执行命令并辅助修改代码。使用时建议让 Agent 在项目目录下工作，而不是只复制单个代码片段。

推荐流程：

1. 项目先维护 Markdown 说明文档
2. 让 Agent 读取项目上下文
3. 进入 Plan Mode
4. 让 Agent 提问并补齐项目框架和技术细节
5. 输出完整规划
6. 保存规划文档
7. 再按规划统一实现
8. 人工检查、测试和调试

不要一上来就让 AI 零碎生成代码。先规划、后实现，可以减少重复函数、混乱命名和后期维护困难。

### 安全注意

安装或运行 Agent 时报错，可以把完整报错交给 AI 分析，但必须先打码敏感信息：

- API Key
- Token
- 密码
- Cookie
- 私有仓库地址
- 服务器地址
- 其他认证信息

工具安装命令、第三方后端配置、API Key 或 provider 配置应以官方文档和当前工具版本为准。
